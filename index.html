01 · Research Question 02 / 17
Where does Spark/GraphX on a five-node Jetstream2 cluster start to help — or stop helping — iterative graph analytics?
RQ 1 · SCALING
How does execution time change as we scale worker count from 1 → 8 on commodity cloud VMs?
RQ 2 · PARTITIONING
Edge-cut (1D) vs vertex-cut (2D): does partitioning strategy matter for communication, balance, and time?
RQ 3 · TOPOLOGY
Does graph shape (power-law vs near-uniform) interact with partitioning and scaling behavior?

Most published GraphX work measures gains on billion-edge graphs. We characterize the lower bound — where distribution begins to cost more than it returns.

06 · Implementation 07 / 17

PageRank — power iteration on GraphX

20 iterations · reset probability 0.15 · forced materialization for honest end-to-end timing.

app/src/main/scala/ecc/Algos.scaladef runPageRank[VD: ClassTag, ED: ClassTag](
    graph: Graph[VD, ED], numIter: Int): String = {

  val ranked = graph.staticPageRank(numIter, resetProb = 0.15)

  // force materialization; top-5 = lightweight checksum
  val top5  = ranked.vertices.top(5)(Ordering.by(_._2))
  val total = ranked.vertices.map(_._2).sum()

  // optional: dump full rank vector for the convergence study
  sys.env.get("ECC_DUMP_RANKS_DIR").filter(_.nonEmpty).foreach { dir =>
    ranked.vertices.map { case (id, r) => s"$id\t$r" }.saveAsTextFile(dir)
  }

  f"top5=[$top5];sum=$total%.6f"   // sum should ≈ |V| → confirms convergence
}
  • ~12 lines of Scala — GraphX provides the heavy lifting; we control partitioning + iteration count.
  • Correctness — top-5 ranks matched NetworkX ground truth on a synthetic 10-node graph; on web-Google, sum of ranks = 875,713 = |V|.
06 · Implementation 08 / 17

SSSP — Pregel BSP on GraphX

Bulk-synchronous label propagation. On roadNet-CA: 726 supersteps = the graph diameter.

app/src/main/scala/ecc/Algos.scalaval weighted = graph
  .mapEdges(_ => 1.0)
  .mapVertices { (id, _) => if (id == srcId) 0.0 else Double.PositiveInfinity }

val sssp = weighted.pregel(
    initialMsg      = Double.PositiveInfinity,
    maxIterations   = Int.MaxValue,
    activeDirection = EdgeDirection.Out
)(
  vprog    = (_, dist, newDist) => math.min(dist, newDist),

  sendMsg  = triplet => {
    val candidate = triplet.srcAttr + triplet.attr
    if (candidate < triplet.dstAttr) Iterator((triplet.dstId, candidate))
    else                             Iterator.empty
  },

  mergeMsg = (a, b) => math.min(a, b)        // commutative + associative
)
  • One full Spark shuffle per superstep. roadNet-CA's diameter of 726 → 726 shuffles → SSSP/roadNet × w=8 emits 3,158 stages & 154,926 tasks.
  • Validation — 1,957,027 of 1,965,206 vertices reachable from source 562818; max distance 726.

08 · Scaling 10 / 17

Negative scaling: more workers = slower

Adding workers should make things faster, or at worst no change. It made things 2–3× slower. Error bars: 95% CIs from 5 trials.

PageRank · web-Google · 1D vs 2D (peak speedup 1.07× at w=2)
SSSP · roadNet-CA · monotonic slowdown — 3.2× worse at w=8
  • PageRank achieves only 1.03–1.07× speedup at w=2 before declining. SSSP shows monotonic slowdown from w=1 onward.
  • Confidence intervals at w=2..4 are disjoint from the no-effect line for SSSP — the negative trend is real, not noise.

10 · Partitioning 12 / 17

1D vs 2D — indistinguishable in our regime

PowerGraph reports 3–100× from vertex-cut on power-law graphs. We saw < 2% on wall time. Why?

Shuffle read volume — 1D vs 2D · all configurations
  • Wall times within 2%; shuffle volume within 50% with no consistent winner.
  • PowerGraph's regime: hub vertices of degree ≥ 10⁴. web-Google's max out-degree: 456 — power-law in shape, but the hubs aren't large enough for 2D's theoretical advantage.
  • roadNet-CA is near-uniform by construction — 2D shouldn't help there at all, and doesn't.
  • Honest framing: we cannot detect a partitioner effect at this scale and skew. We do not claim 1D ≡ 2D in general.
11 · Engineering Win 13 / 17

The one knob that actually moves the needle

spark.locality.wait defaults to 3 seconds — assuming HDFS-style data locality. We read from NFS. Locality doesn't exist.

Configuration · PR/web-Google/1D/w=4Wall time (n=5)Algo time (n=5)Δ
Default · locality.wait = 3s37.6 ± 8.7 s26.0 ± 7.7 s—
Tuned · locality.wait = 0s25.7 ± 0.8 s15.2 ± 0.3 s−31.7%
  • Confidence intervals are disjoint — this is real, not noise.
  • Doesn't change the headline (Spark still 19× slower than scipy on this cell, vs 27×) but recovers ~⅓ of the gap.
  • Practitioner takeaway — on NFS-backed Spark, locality.wait=0 is mandatory. It's a real-world configuration trap.
  • Effect only at w ≥ 2 (at w=1 there's a single executor — nothing to wait for).

13 · Conclusion 15 / 17

What this study tells an engineer

Not "Spark is bad" — "Spark has a regime, and we measured the lower bound."

PRACTITIONER TAKEAWAY
At sub-RAM graph scale (~5M edges), Spark's framework overhead is 25–400× the single-machine algorithm time, and adding workers makes it worse, not better.
The slowdown isn't GC (<2.5%) and isn't shuffle-wait (<2.7%) — it's per-task overhead dominating when a 5M-edge graph is chopped into 150K tasks.
Spark begins to pay only when the working set exceeds single-node RAM — which our datasets do not. Choose single-machine implementations until you cross that line.
